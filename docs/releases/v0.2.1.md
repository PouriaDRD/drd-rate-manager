# DRD Rate Manager v0.2.1 — Release Notes

`v0.2.1` is a corrective hardening and configuration-management release on the `0.2.x` line.

This document describes the release candidate prepared on `dev`. It is not considered production until the tested `dev` candidate is promoted to `main`, deployed from `main`, and completes post-deploy verification.

## Release identity

- Application version: `0.2.1`
- Public API version: `v1`
- D1 schema: `13`
- Runtime Settings Catalog: `3`
- Secure Settings Catalog: `1`

There is no destructive D1 schema migration in this release.

## Highlights

### Full configuration management

The private Web Admin manages all 25 Runtime Settings and the status/replacement workflow for all 4 encrypted Secure Settings. All 13 provider endpoints and CoinGecko runtime configuration are represented.

Secure settings are replace-only; existing plaintext is never returned. Sensitive replacement requires current-password confirmation. `APP_MASTER_KEY` remains infrastructure-owned, status-only in the UI, and must remain configured.

### Browser and integration hardening

Playwright E2E coverage exercises the private Web Admin in Chromium, Firefox, and WebKit, including boot/session gating, feature activation, configuration, session expiry, error states, and mobile navigation.

### Market/cache resilience

This release hardens refresh coordination and stale-cache fallback. Refresh-lock or cache-write storage failures can preserve a usable prior snapshot, while absence of usable cache still fails closed.

Consensus semantics remain unchanged: 7 USDT providers, 6 Gold providers, median consensus, and 3% outlier rejection when at least 3 healthy samples exist. Nobitex and MelliGold remain opt-in.

### Security and failure semantics

Expired and credential-version-mismatched sessions are invalidated consistently. Invalid CSRF does not delete an otherwise valid session. Failed configuration persistence cannot produce a false-success audit event, and audit/history persistence failures do not replace the primary operation result.

### Telegram routing

Ordinary text is ignored outside active input flows, unknown slash commands do not open the menu, and unrelated commands do not consume pending admin/token/channel input.

### Documentation and release tooling

The repository now includes full Persian/English manuals and specialist documentation. Version tooling is dry-run by default, uses explicit targets, updates live identity/current-release assertions, preserves historical fixtures, and requires `--write` to mutate files.

## Compatibility

This is a patch release. External API remains `v1`; D1 schema remains `13`.

Runtime Settings Catalog is `3`. During mixed-version staged rollout, old and new Workers may share D1 and older production code may temporarily rewrite older catalog metadata. Candidate readiness should be validated using candidate code and metadata must be verified again after promotion. A future change should make metadata writes monotonic/downgrade-safe.

## Release procedure

1. complete all gates on `dev`
2. verify release identity and clean diff
3. strict-preflight the real production Wrangler config
4. create a fresh remote D1 backup
5. upload a candidate with 0% production traffic
6. run version-override smoke/integration checks
7. verify runtime/secure migration readiness
8. promote `dev` to `main`
9. production deploy/promotion only from `main`
10. run post-deploy smoke and metadata verification
11. retain the known-good rollback candidate until verification completes

Preparing or committing this file performs no Cloudflare deployment.

## Post-promotion cleanup

Legacy Worker secrets must remain until the new production release is promoted and verified.

Before separately approved cleanup, verify runtime catalog `3`, all 25 runtime settings, secure catalog `1`, all 4 secure settings, no legacy secure fallback, and no migration blockers.

`APP_MASTER_KEY` must remain configured and must never be removed or regenerated as part of cleanup.
